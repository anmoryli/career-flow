# 职序 V1 Agent 设计讨论稿

用户已确认沿用 PydanticAI 开发 V1，部署目标为 4C4G；固定任务流程开始分阶段实现，本文不是完整 Agent 系统的验收声明。用户端仍以简历、岗位、报告和求职工作台为主；AI 仅在需要理解文本或生成建议的步骤出现。

## 推荐方案：固定任务流程 + 一个受控模型适配层

沿用已有 Flask/MySQL/RQ/PydanticAI。每项任务由服务端状态机推进：读取授权材料 → 构造受限上下文 → 报价与用户确认 → RQ 执行模型 → Pydantic 校验 → 用户核实建议 → 保存版本或报告。模型不能决定账务、权限、数据删除或配置发布。

任务按功能分开：简历字段提取、简历优化、JD 解析、岗位诊断、追问、报告、对话摘要、记忆提取和结构化表单。可先共用一个模型，后台逐步为功能配置模型路由；不引入 OpenClaw，也不让多个 Agent 在 V1 中自由互相发起调用。

## 成本控制

- 简历、岗位和已确认事实只取本次任务必需部分；复用已解析的 PDF/JD 和已完成报告。
- 诊断每轮最多一个问题，累计最多 10 轮，跳过也计数。没有新增信息时结束追问，避免模型空转。
- 每次收费任务先显示最高积分，再确认、冻结、执行、按供应商实际用量结算；失败按现有规则释放。后台配置每个功能的模型、输出上限、超时、重试和单次费用上限。
- 超长对话先用确定性裁剪保留最近消息及已确认事实；确需摘要时单独计量并保留版本，不把模型推测写成事实。
- 不向供应商发送照片、隐藏模块、与当前任务无关的历史记录或其他用户数据。

## 工具与数据边界

服务端仅注册小粒度工具，例如读取当前用户授权的简历版本、已确认 JD、当前诊断答案，以及提交一份待确认的结构化建议。工具参数和输出均由 Pydantic 校验，执行时再次检查用户和对象权限。外部文档及模型结果始终按不可信数据处理。用户确认前，建议不得直接改写原简历。

MySQL 保存对话、消息、任务、工具调用摘要、提示词版本、用户确认事实和费用流水。对话摘要与长期记忆区分“用户事实”“AI 推测”“待确认”；删除后的数据不能再次进入检索。Redis 只承载队列和短期限流。

## 管理端与用户界面

管理员维护模型服务商与密钥、按任务的模型路由、提示词草稿/测试/发布/回滚、Token 与费用上限、任务失败记录和审计。发布版本不可变，正在执行的任务使用其确认时的版本。密钥只在服务端加密存储，不出现在页面或日志。

用户看到的是“导入并核对简历”“对照岗位”“查看依据”“采纳/编辑建议”等操作。诊断追问使用有限的结构化表单；通用对话是补充入口，不替代编辑器和任务页面。
